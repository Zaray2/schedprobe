# FuzzLab：静态分析与队列反馈辅助 Fuzzing 调度

在**同一目标、同一初始语料、同一执行预算**下，比较六种"下一个 fuzz 哪个种子"的策略。

**核心结论（先放在这里，细节在后）**：

> **假设 H1 被证伪。** 用静态结构特征选种子**显著更差**——比简单轮询少 37 条边，
> 且超出种子离散度。用队列反馈（新颖度+防饥饿）**不显著优于轮询**（+2.7 边，落在离散度内）。
> 也就是说：**在这个目标上，"种子的多样性"比"种子的结构分数"更重要，而简单轮询很难打败。**
> 缺陷指标因为**零崩溃**而没有数据——如实报告，不做任何推断。

---

## 1. 研究问题与假设

### 1.1 问题

Fuzzer 每轮要决定：**下一个变异哪个种子**。AFL++ / libFuzzer 的默认调度只看执行反馈
（命中次数、边覆盖、执行速度），**不看输入的语法结构**。

**问题**：把输入的结构特征与队列老化状态纳入调度，在固定执行预算下能否得到更多边覆盖与更多独特缺陷？

### 1.2 假设与结果

| 编号 | 假设 | 结果 |
|---|---|---|
| H1 | 结构+反馈策略在固定预算下提高边覆盖 | **被证伪**：静态部分显著更差 |
| H2 | 同样策略提高独特缺陷数 | **无数据**：所有策略零崩溃 |
| H3 | 收益可拆为"静态"与"反馈"两部分 | **成立且方向明确**：收益只可能来自反馈；加静态反而无增益 |

## 2. 两种干预点，以及为什么第一次失败

### 2.1 第一次尝试：AFL++ 的 `afl_custom_queue_get`（失败）

原计划把调度做成 AFL++ 插件，用官方准入钩子。实测结果：

- 第一版插件**完全没生效**：缺 `afl_custom_fuzz` 符号，AFL++ 打印
  `WARNING: Symbol 'afl_custom_fuzz' not found` 后**从不调用队列钩子**。
  五个臂各跑 1 万次以上执行，记录的调度决策数 **0–2 次**——"实验组"和"基线"跑的是同一个 fuzzer。
- 补上符号后钩子开始被调用，但**20 秒 1860 次执行里只有 2 次决策**。该钩子每队列轮次
  每条目只调用一次，而 AFL++ 绝大部分时间耗在单条目的 havoc 上。

**结论：这个钩子不能作为逐种子调度的干预点。** 相关代码与数据保留在
`fuzzlab/hooks/`、`docs/research/fuzzlab-data/fuzzlab-runs.*`，作为失败案例存档。

### 2.2 第二次尝试：自建调度循环（本文的主实验）

libFuzzer 没有任何调度钩子，其 `LLVMFuzzerMutate` 也无法独立调用（依赖内部驱动状态）。
所以调度循环由本项目实现，但**只实现调度所必需的那一层**：

| 组件 | 来源 | 是否研究对象 |
|---|---|---|
| 覆盖率插桩 | clang `-fsanitize=fuzzer-no-link`（SanitizerCoverage） | 否，外部成熟组件 |
| 崩溃检测 | ASAN，在 fork 出的子进程里 | 否，外部成熟组件 |
| 变异算子 | 教科书 havoc 集合（位翻转/字节替换/插入/删除/拼接） | 否，**刻意保持恒定** |
| **种子调度** | **本项目** | **是** |

变异保持恒定是刻意的：变聪明只会让调度差异更难观察，并给读者第二个解释每个结果的理由。

## 3. 调度策略设计

六个策略共享**同一个字节完全相同的二进制**，只靠一个策略字符串区分：

| 策略 | 规则 | 角色 |
|---|---|---|
| `libfuzzer` | 真 libFuzzer 自身默认调度 | **基线 B（外部）** |
| `fifo` | 永远变异最老的种子 | 退化基线 |
| `rr` | 轮询 | **基线 A** |
| `static` | 静态结构分最高者优先 | 消融 |
| `feedback` | 按"新颖度×0.6 + 防饥饿×0.4"加权随机 | 消融 |
| `full` | 静态与反馈各 0.5 | **实验组 C** |

### 3.1 静态特征（`sched_loop.c: static_score`）

| 特征 | 定义 | 权重 |
|---|---|---|
| 结构密度 | `{ } [ ] " : ,` 占长度比例 | 0.45 |
| 字节多样性 | 不同字节值数 / 64 | 0.30 |
| 嵌套深度 | 最大括号深度 / 16 | 0.20 |
| 控制字符密度 | 非打印字符占比 | 0.05 |

只用字节统计：零成本、不解析、不与目标语法绑定。

### 3.2 反馈特征

| 特征 | 定义 | 权重 |
|---|---|---|
| 新颖度 | `创建序号 / 队列大小`（创建序号只在发现新覆盖时前进） | 0.6 |
| 公平性 | `1 / (1 + 已变异次数)` | 0.4 |

### 3.3 确定性

两个策略都是加权随机，RNG 由 `(种子, 迭代序号)` 初始化。没有时间、pid、地址。
同一配置重跑得到同一决策序列。

## 4. 实验环境与复现

| 项 | 值 |
|---|---|
| 宿主 | Windows 11 / Python 3.14 |
| Fuzzing 环境 | WSL2 + Alpine Linux (musl) |
| 编译器 | clang 22.1.3 |
| 目标 | **cJSON 1.7.19，源码编译** |
| 源码 SHA256 | `7fa616e3046edfa7a28a32d5f9eacfd23f92900fe1f8ccd988c1662f30454562` |
| Sanitizer | ASAN |
| **预算** | **每 campaign 10,000 次执行**（不是墙钟秒数） |
| 种子 | 1337 / 1338 / 1339 |
| 起始语料 | 6 个结构不同的 JSON，覆盖三条解析路径 |

**为什么用执行次数而不是墙钟**：本循环每次执行都 fork，libFuzzer 是进程内执行，
两者速度差约 200 倍（165 vs 39,601 次/秒）。用墙钟预算测到的主要是 fork 开销，
那会被误报成调度结果。

```bash
PYTHONPATH=src python scripts/fuzzlab_loop_run.py build
PYTHONPATH=src python scripts/fuzzlab_loop_run.py run --execs 10000 --seeds 3
```

## 6. 结论与消融

### 6.1 H1 被证伪

静态策略（237.33）比简单轮询（274.67）**少 37 条边，且超出其离散度 5**。这不是噪声：
**用结构分数挑种子会让 fuzzer 反复变异"看起来最像 JSON"的那几个，饿死其余**，
而解析边界往往在结构不规整的种子上。

`fifo`（238.0）与 `static`（237.33）几乎相同——两者都是"反复选同一类种子"，
只是一个按年龄、一个按结构分。**这条一致性是结论内部自洽的证据**。

### 6.2 收益（如果有）只来自反馈

| 对比 | Δ |
|---|---|
| `feedback` vs `rr` | **+2.66**（落在离散度内） |
| `full` vs `rr` | **+1.33**（落在离散度内） |
| `full` vs `feedback` | **-1.33**（加上静态反而略降） |

消融方向明确：**H3 成立——静态分析没有贡献，反馈有一点点（但不显著）**。

### 6.3 关于 libFuzzer

`libfuzzer` 263.67，`rr` 274.67，Δ = -11.00，**落在离散度 12 以内**。
所以只能说"本循环的轮询与 libFuzzer 默认调度没有可分辨的差异"，
**不能说我们超过了 libFuzzer**。这是一个诚实的边界。

### 6.4 缺陷指标：无数据

六个策略、18 场 campaign、18 万次执行，**零崩溃**。cJSON 1.7.19 在这个预算下
没有可发现的缺陷信号。H2 完全没有数据，本文不作任何推断。

## 7. 失败案例与已修复的缺陷

**每一条都曾产生过看起来合理但错误的数字。**

1. **系统 cJSON 包未插桩 ⇒ fuzzer 是瞎的。**
   链接 Alpine 的 `libcjson.so` 时只有 30 行驱动被插桩，AFL++ 报
   `Bitmap range : 5 to 5 bits`。构建阶段现在用 `total_edges >= 200` 自检。

2. **AFL++ 插件惰性**（§2.1）：缺符号 ⇒ 钩子从不被调用 ⇒ 五臂等价。

3. **fork 后覆盖率计数器丢失。**
   第一版循环用 fork 执行目标，却读父进程的计数器——子进程的 COW 写入全部丢失，
   1097 条边的目标只报告 11 条边。修法：子进程通过管道把自己的计数器数组回传。

4. **崩溃计数把 0 字节文件算成崩溃。**
   `find -size +0` 在 busybox 上未按预期工作，把 LeakSanitizer 的空复现产物
   计成了 libFuzzer 的一个"崩溃"。修法：`-not -empty`，并在 `ignore_crashes=1` 下跑满预算。

5. **覆盖率指标口径不一致。**
   某次试点中 libFuzzer 走了"按函数累加"的兜底路径，得到 117 条边，与循环的 282 条
   不是同一个量。修法：只认 `#N DONE cov:` 那一行。

6. **失败时销毁现场**：早期无论成败都删 WSL 工作目录，把解释失败的日志一起删了。
   现在只有成功才清理。

7. **本流程自身的教训**：有一次我改完 README 没重跑全量就提交，CI 在 200 行预算上挂了。
   现在提交前必跑完整门禁。

### 7.1 结构性局限

- 单目标（cJSON）、单变异集合、单平台。
- 10,000 次执行 × 3 种子是小样本；本文只报均值与极差，**不宣称统计显著性**。
- 交叉点：本文的"轮询很强"是在**小语料、短预算**下测的。语料很大时轮询会变差，
  这是下一步要测的。

## 8. 下一阶段计划

1. **放大语料与预算**，检验"轮询随语料增大而退化"这一预测——这是本实验最直接的
   可证伪推论。
2. **换有已知缺陷的目标版本**（cJSON 1.7.17，早于 1.7.18 修复），让 H2 有信号。
3. **多目标复验**（libxml2），检验"静态有害"是否只是 cJSON + 本变异集合的产物。
4. **提高执行速度**：把 fork 换成持久化模式 + 信号恢复，让同样预算能覆盖更多轮次。
