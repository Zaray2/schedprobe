# 基准实验结果（可复现）

本文件记录 `schedprobe` 内**四种调度策略**在**确定性模拟网络**上的实测对比。
原始数据：[`benchmark-raw.json`](benchmark-raw.json)（完整 JSON）与
仓库根的 `bench-published.txt`（人读版，由脚本生成，未纳入版本控制）。
复现命令见文末。

## 1. 这是什么的基准，不是什么

**是**：同一份随机种子、同一个合成网络、同一个预算下，本项目自带的四种调度器之间的相对差异。
目标端是模拟后端，因此结果与机器、网络、时间无关，同一版本重跑会得到相同数字。

**不是**：与 Nmap / Masscan / RustScan / Naabu 的对比。那些工具**没有在本环境中运行过**，
任何"比 X 更快/更准"的说法在这里都没有依据。本项目测的是"调度策略"这一层。

同样重要：**模拟后端的成本是模型，不是墙钟时间**。本文件所有"成本"都是该模型的计费单位
（一次被丢弃的探测记满一次超时，一次成功的连接只记一个往返）。模型见
`src/schedprobe/backends/fake.py` 的 `_cost()`。

## 2. 实验设置

| 项目 | 值 |
|---|---|
| 工具版本 | 0.1.0 |
| 后端 | `fake`（确定性模拟，零网络访问） |
| 随机种子 | 1337 |
| 对照策略 | `adaptive`（本项目）/ `fixed`（输入序）/ `random`（打乱序）/ `fixed-longtimeout`（输入序 + 长超时） |
| 剪枝模式 | `defer`（默认） |
| 确认探测 | `confirm_min_attempts=1`，且仅当"超时与所在段既有模式矛盾"时才重探 |
| 预算预留 | `reserved_ratio=0.15`（扫描阶段上限 = 预算 × 0.85，确认阶段放开至完整预算） |
| 并发 / 超时 | 128 / base 0.6s、min 0.15s、max 3.0s |

场景定义见 `src/schedprobe/backends/fake.py` 的 `builtin_scenarios()`——场景是**数据**，
读者可逐主机、逐端口核对地面真值。

## 3. 主结论：达到"全召回"所需的成本

这是本基准认为最公平的单一比较点：在所有策略都给出正确答案的那一点上，各自付了多少。
"—"表示**即使把预算加到该场景最高档位也没能达到全召回**。

| 场景 | 开放端口 | adaptive | fixed | random | fixed-longtimeout |
|---|---|---|---|---|---|
| `blackhole-segment` | 10 | **8,508** | 50,501 | 48,717 | 50,501 |
| `segmented-sweep` | 3 | **9,054** | —（20 万仍 0%） | —（20 万时 33%） | — |
| `mixed-lossy` | 3 | **9,448** | —（67%） | —（67%） | — |
| `segmented-filtered` | 12 | 94,331 | **63,701** | 97,901 | **63,701** |
| `wide-sweep` | 3 | —（33%） | —（67%） | —（0%） | —（67%） |
| `healthy` | 7 | **49** | 49 | 49 | 49 |

### 结论（含负面结果）

1. **"大范围空间里大部分是死的"这类场景，自适应策略明显更省。**
   `blackhole-segment`：**8,508 vs 50,501**，同样 100% 召回，成本约为基线的 **1/6**。
   `segmented-sweep`：15,000 预算即可全召回，而固定序扫描给到 200,000 也**一个都没找到**——
   它把整个预算花在了开头那段被丢弃的 /24 上。`mixed-lossy` 上只有自适应达到 100% 召回。

2. **"整个空间都同样敌对"的场景，自适应策略更差。**
   `wide-sweep`（3 台主机各 1024 端口，绝大多数被丢弃）：自适应 33%，固定序 67%。
   原因是这个场景里"坏段"就是全部扫描范围，剪枝无从下手，而确认与段间调度的开销没有收益。

3. **"段内大部分死、少数活"的场景，两者接近、固定序略优。**
   `segmented-filtered`：自适应需 94,331 到 100%，固定序 63,701。
   但**低预算区间自适应更好**：15k–80k 时自适应稳定 92%，固定序停在 58%。

4. **无敌意网络下四种策略无差别**（都是 49）。说明自适应策略的开销来自"处理死空间"，
   而不是策略本身。

5. **精度在所有单元格中均为 100%**：模拟后端不会凭空制造开放端口，所以任何一个
   "报了 open 但地面真值不是 open"的判定都意味着调度器或引擎缺陷——这正是基准
   同时记录 precision 的原因。

## 5. 这些数字是怎么被"挣到"的（工程记录）

策略不是一次写对的。基准在开发过程中反复**证伪**了早期设计，以下四条是基准发现并修掉的
真实缺陷（`CHANGELOG.md` 有对应条目）：

1. **段健康度公式方向反了。** 初版 `confidence_ema·√(1+productive) − waste_ratio`
   会让"整段被丢弃"里少数存活主机的分数变小、反而被优先探测；首次基准跑出
   adaptive 召回 20% vs fixed 70%。现公式见 `models.SegmentState.health_score`，
   单元测试固定其单调性。
2. **启动批次一次花掉大部分预算。** 初版会把在途探测一次性填满到并发上限，
   于是在还没观测到任何结果时，预算就可能被压在同一个未评估的段上。
   现在启动波次由"还有多少段未被评估"决定（`engine._wave_size`）。
3. **无差别确认探测吃掉扫描预算。** 对每个超时都做一次更长窗口的重试，在死段上等于双倍开销：
   `blackhole-segment` 召回因此从 100% 掉到 60%。现规则是"只在超时与所在段既有模式矛盾时
   才确认"（`config.confirm_max_drop_ratio`）。
4. **预算预留只被记录、没有接线。** `reserved_ratio` 曾只出现在 run-header 里，
   扫描阶段照样花完整预算，预留等于不存在。现在扫描阶段上限为 `budget − reserve`，
   确认探测开始时才放开（`engine._has_headroom`），回放按同一事件切换
   （`CostLedger.sweep_cap`）——否则 72 组不变量组合里的回放校验会立刻失败。

## 6. 复现步骤

```bash
# 全量：预算档位扫描 + 头部用例，写入 bench/ 与 docs/research/benchmark-raw.json
python scripts/run_published_bench.py

# 单个场景
python -m schedprobe bench --scenario blackhole-segment --budget 80000
```

`scripts/run_published_bench.py` 只使用确定性模拟后端，不产生任何网络流量。

## 7. 已知的基准局限

- **只有模拟后端。** 真实网络的丢包模式、中间设备行为、TCP 栈差异都不在模型里。
  用真实后端跑出的单次结果**不能**与本文表格并列比较。
- **地面真值由场景文件定义。** 场景是人工构造的，覆盖取决于作者想到了哪些组合；
  欢迎以 PR 补充场景（见 `CONTRIBUTING.md`）。
- **成本模型是计费的、不是墙钟的。** 模型取最坏情况，这对所有策略是同一套规则，
  因此相对比较有效，但绝对秒数不代表真实扫描耗时。
- **没有做统计显著性检验。** 模拟后端是确定性的，同一配置重复运行结果完全相同，
  因此"同一配置的方差"为零；但**跨场景**的差异不能被当成总体结论——本文件因此逐场景
  列出结果，不给聚合平均分，也不声称"自适应策略普遍更好"。
- **`adaptive` 的负面结果被保留**（`wide-sweep`、`segmented-filtered` 高预算段）。
  如果本项目只发布对它有利的场景，这张表就失去了意义。
